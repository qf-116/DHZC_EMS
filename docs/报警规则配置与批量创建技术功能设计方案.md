## 0. 给开发模型的执行指令

### 0.1 开发目标

将现有 `/alarm-rules` 报警规则配置页面升级为：

1. **单条规则可靠配置**：用户在新建或编辑弹窗中输入的内容必须真实保存、发布、触发和追溯。
2. **同类指标批量创建**：支持多台设备上的相同或同类指标一次生成多条独立规则草稿。
3. **规则状态可治理**：草稿、校验、发布、停用、版本、批次和审计信息通过 DemoStore/reducer 管理。
4. **报警恢复条件完善**：区分恢复判定、稳定确认、业务闭环和最终关闭。
5. **前端演示自洽**：不实现真实后端、MQTT、WebSocket、真实审批接口或真实历史回放服务；所有交互通过现有 DemoStore 演示状态机实现。

### 0.2 必须遵守的项目约束

- 技术栈保持 React 19 + Ant Design 6 + Vite 7 + HashRouter。
- 页面不得绕过 `DemoStore` 直接修改业务事实；所有规则保存、发布、停用、批量提交必须经 `actions.js` → `reducer.js`。
- 不使用 `Date.now()`；使用现有 DemoStore 演示时钟和 `meta.demoDay`。
- 保留点检、保养、巡检页面、菜单、路由和需求细则，不得借本任务删除或改动这些模块。
- 不改动监测大屏的样式、文案和“演示数据”标注。
- 不引入真实后端能力；审批、回滚、历史回测等使用前端演示数据和状态机表达。
- 规则批量创建默认“只生成草稿，不直接发布”。
- 批量操作默认“仅新增，不覆盖已有规则”。覆盖、更新、停用必须单独确认。
- 每完成一个稳定阶段运行：
  ```bash
  npm run build
  node check-pages.cjs
  ```
- 当前项目全路由烟测以仓库中的 `check-pages.cjs` 为准，不要在文档中硬编码过时的路由数量。
- 每个稳定阶段本地 `git add -A && git commit`；除非用户明确要求，不推送 GitHub。

### 0.3 开发顺序

不得先把单选指标简单改成多选。必须按以下顺序开发：

```text
阶段 P0-1：统一表单模型与单条规则真实保存
阶段 P0-2：规则校验、原子保存/发布、版本快照
阶段 P0-3：恢复条件和治理配置结构化
阶段 P1-1：批量范围选择、同类指标分组、预览
阶段 P1-2：批量生成草稿、批次结果、逐条调整
阶段 P1-3：批量发布、灰度/回滚演示、审计
```

如果时间有限，先完成 P0，再实现 P1；不得以未落库的演示控件冒充已经完成的批量能力。

### 0.4 Council + 业务专家评审结论（必须遵守）

本方案已由架构正确性、前端实现、反方风险和设备管理业务专家共同评审。结论为：

> **业务方向正确，不能按当前 V1.0 全量一次性实施。必须先完成“小而真”的单条规则闭环，再实现受限的同类指标批量 MVP。**

原因不是批量创建思路错误，而是现有 DemoStore 还没有承载以下关键事实：

- 规则草稿和当前生效版本分离；
- 规则目标的 canonical `deviceId + bindingId/version + sourceId + metricCode/version`；
- 已发布规则和有效绑定的触发门禁；
- 可执行的恢复稳定计时、质量要求和再次超限处理；
- 完整的规则/通知/恢复事件不可变快照；
- 批量任务、逐目标结果和幂等提交。

因此，开发模型不得将本节之后的全部字段都一次性做成“看起来可配置”的控件。没有状态、action、reducer、持久化和验收闭环的字段，必须暂时隐藏、禁用或标记为“演示占位”，不得使用成功 toast 冒充已完成。

#### 推荐 MVP 范围（必须先完成）

MVP 只实现以下能力：

1. 数值型阈值规则：越上限、越下限；区间外可作为第二步，不作为第一批必做项。
2. 单条规则：受控表单、canonical 目标、触发阈值/持续时间、恢复阈值或回差/稳定时间、固定已有通知策略。
3. 规则状态：独立的草稿和当前已发布版本；只有已发布且绑定有效才能触发。
4. 发布：单个 reducer 原子命令，发布失败保留草稿和弹窗；发布写最小不可变版本快照。
5. 恢复：只实现“满足恢复阈值 + GOOD 数据持续稳定”的最小判定；无效数据默认保持报警，重新超限则恢复计时归零。
6. 批量：仅允许完全匹配的同类目标（同 canonical 指标模板、数据类型、单位、量程、设备型号和触发模式），逐目标预览，生成多条独立草稿，已有规则默认跳过。
7. 验收：补充纯 Node reducer/domain 契约测试，覆盖保存、发布、触发门禁、恢复、版本快照和批量幂等；浏览器烟测只作为补充。

#### MVP 明确后置或禁用的内容

以下内容在没有真实数据模型和动作闭环前，不得作为第一阶段完成项：

- 组合 AND/OR 规则；
- 质量规则多模式；
- 状态枚举规则；
- 规则级通知临时覆盖、静默覆盖和复杂升级；
- 报警风暴跨设备合并；
- 模板 CRUD 持久化；
- 批量发布、灰度、回滚、审批；
- 历史数据回放回测；
- 真实短信/电话/邮件发送。

这些入口若保留，必须显示“演示占位/暂未实现”，并且不写入虚假的成功业务事实。

#### 评审发现的四个阻断项

1. `RuleConfigPage.jsx` 先保存后立即发布，配合 actions 闭包旧 state 会导致发布竞态；必须使用 `alarm/rule/saveAndPublish` 原子命令，或拆为两个明确用户动作。
2. 当前 `alarmRulesById[ruleCode]` 单实体模型无法同时保存“当前已发布版本”和“编辑草稿”；已发布规则编辑不能直接覆盖当前实体，必须建立 `currentPublished`/`draft` 指针或等价模型。
3. 当前 `alarm/raise` 只检查规则存在，未检查已发布状态、绑定启用、目标匹配和指标有效性；草稿/停用/任意设备不可触发必须成为 reducer 门禁。
4. 当前 `alarm/recover` 只根据文本 evidence 立即恢复，未执行稳定时长、质量码、再次超限归零和业务关闭门槛；MVP 先实现最小可执行恢复状态机，不得只扩展页面文案。

#### 评审发现的关键兼容契约

- 规则页不能继续把 `standardData.netBindings` 作为编辑事实；必须通过 DemoStore 的正式 binding selector。若正式 binding 的内部 `sourceId` 与展示 `sourceCode` 并存，文档和代码必须明确二者含义，不得混用。
- 旧种子中的“程序、备件、点检、保养、维修”等业务规则不能被默认映射成阈值规则。第一阶段应将暂不支持的旧业务规则设为只读，或提供明确的 legacy adapter；不能打开后静默改写语义。
- `metric.dataType`、单位、量程等元数据存在中文展示值与结构化值的差异时，必须先定义 adapter/normalize 函数，不能直接比较不同形态。
- 新增结构化字段必须提供 legacy normalize/projection 策略，并说明 DemoStore `STORE_VERSION` 升级和旧 localStorage 快照处理；不得默认整包丢弃而不提示。
- 批量提交采用“单批次、逐目标隔离”的部分成功语义：目标级校验失败不写半条规则，其它合法目标可生成草稿；批次必须记录每个目标的 `created/skipped/blocked/failed`、错误原因、`batchId` 和 `clientRequestId`。重复提交同一请求返回原结果，不得重复生成。
- 已发布规则编辑必须保留旧版本可继续解释历史报警；新草稿发布后才切换当前生效指针。新规则首次发布版本为 `V1`，版本号规则必须在 reducer 契约测试中固定。

#### 开发前必须先冻结的契约

在 GLM-5.3 Flash 开始改页面前，先在代码中确认并记录以下契约；如果现有实现与本节不一致，先修契约，不要让模型自行猜字段：

1. **目标主键契约**：`deviceId` 使用 `DEV-*` canonical ID；`bindingId` 是绑定实体 ID；`bindingVersion` 是绑定版本；`sourceId` 使用绑定实体内部来源 ID；`sourceCode` 只作展示；`metricCode`/`metricVersion` 来自当前启用绑定。不得把 `MT*` 资产编码当作 `deviceId`。
2. **规则版本契约**：建议保留 `alarmRulesById[ruleCode]` 作为规则索引，但增加 `draftByRuleCode` 和 `currentPublishedVersionByRuleCode` 指针，或采用等价的 `ruleDraftsById`/`ruleVersionsById` 结构。已发布编辑不能覆盖当前发布快照。
3. **Action 结果契约**：现有 `dispatch` 若不返回 reducer 结果，不能直接声称 `actions.*` 已返回真实 `{ok,message,refs}`。MVP 应采用“action 创建器返回 request，页面从 `meta.lastAction` 读取结果”，或重构 store 使 dispatch 同步返回 reducer 结果；保存、发布、批量提交必须统一一种方式。
4. **版本号契约**：新规则第一次发布必须为 `V1`；已发布规则生成新草稿并发布为 `V2`。草稿保存不能提前消耗发布版本号。
5. **旧规则契约**：现有 `程序`、`备件`、`点检`、`保养`、`维修`等非阈值业务规则，MVP 设为只读并显示“暂不支持编辑”；或者先实现明确的 legacy adapter。禁止通过 `RULE_TYPE_KEY` 默认回退为阈值规则。
6. **元数据契约**：先定义 `normalizeMetricMeta()`，统一中文/英文数据类型、字符串/对象量程、单位和采样周期。批量分组只能使用归一化结果，不能直接比较展示字符串。
7. **迁移契约**：提高 `STORE_VERSION` 前先写 `normalizeLegacyRule()` 和 localStorage 迁移/重置提示；同版本快照也要做最小结构校验。迁移失败必须可解释，不能静默丢失用户草稿。
8. **部分成功契约**：批量是“一个 batch action 内逐目标隔离”的部分成功，不是 all-or-nothing。每个目标先完成校验，失败目标不写实体，合法目标生成独立草稿；结果保存后，重复 `clientRequestId` 直接返回原结果。
9. **时间契约**：恢复稳定时间使用 DemoStore 演示时钟和结构化计时字段；不能用 `Date.now()` 或通过嵌套 reducer action 让一次业务动作重复推进演示时间。一次业务动作只推进一次 `tick`，维修验收联动报警恢复应在同一 reducer case/纯函数中完成。
10. **时区契约**：演示基准固定为 `+08:00`，时间格式化不能依赖浏览器本机时区；file:// 在其它时区打开时仍必须显示同一演示时间。所有动作、时间线、SLA 和恢复证据使用同一 `at`。

- **不是直接批准 V1.0 全量开发**，而是 `Request Changes → 按 MVP 分阶段实施`。
- MVP 通过前，不得把组合、质量、状态、复杂通知、模板、回测、批量发布等入口作为已完成需求验收。
- 业务专家需要在 MVP 验收前确认四个现场口径：边界使用 `>` 还是 `>=`；BAD/无数据时恢复计时如何处理；哪些维修/停机状态算业务闭环；升级通知的接收组、静默例外和取消条件。

## 1. 现状与问题基线

### 1.1 当前页面和状态层

- 页面：`src/pages/RuleConfigPage.jsx`
- 页面路由：`/alarm-rules`
- 规则实体：当前 DemoStore 中使用 `entities.alarmRulesById`。
- 规则版本：当前使用 `entities.alarmRuleVersionsById`。
- 规则动作：`src/state/actions.js` 中已有单条 `saveRuleDraft`、`publishRule`、`disableRule` 等动作。
- Reducer：`src/state/reducer.js` 中已有 `alarm/rule/saveDraft`、`alarm/rule/publish`、`alarm/rule/disable`。
- 领域层：`src/domain/alarm.js` 已有报警事件状态机、去重键和关闭前置校验，但尚未形成完整规则配置校验器。
- 绑定事实：正式设备绑定数据位于 `src/data/demo/bindings.js` 及相关 selector；旧的 `standardData`/`demoData` 仅可作为兼容种子，不能继续作为规则编辑后的事实来源。

### 1.2 已确认的高优先级缺陷

以下问题必须在批量功能之前修复：

1. **保存后立即发布读取旧状态**
   - `RuleConfigPage.jsx` 的保存流程先调用 `actions.saveRuleDraft`，再立即调用 `actions.publishRule`。
   - React 状态更新尚未完成时，后一个 action 可能读到旧的 DemoStore，导致“规则不存在”或“只有草稿可发布”。
   - 发布失败后当前页面仍可能关闭弹窗，用户容易误判发布成功。
   - 解决：增加 reducer 原子动作 `alarm/rule/saveAndPublish`，或明确拆成“保存草稿后再点击发布”；推荐原子动作。

2. **规则名称和等级没有绑定真实状态**
   - 当前名称、等级部分使用 `defaultValue`。
   - `saveRule` 主要从 `editing` 或默认值构造，可能导致新建名称固定为“新规则 N”、等级无法按输入保存。
   - 解决：统一 `ruleForm` 受控状态，保存时只从表单模型读取。

3. **编辑打开没有完整回填**
   - 当前 `openEdit` 没有完整回填设备、来源、指标、触发模式、阈值、区间、持续时间、回差、抑制、风暴、静默、质量和组合条件。
   - 会出现“上一次操作残留值 + 当前 editing 旧字段”的混合规则。
   - 解决：所有新建/编辑都通过 `createEmptyRuleForm()` 或 `ruleToForm(rule)` 初始化。

4. **触发与恢复字段显示可编辑但不完整落库**
   - 当前新建规则可能只拼接 `condition` 文本，无法表达 upper/lower/range/state/quality/combo 的真实结构。
   - 恢复方式、恢复持续时间、回差也没有完整结构化保存。
   - 解决：使用 `triggerConfig`、`recoveryConfig` 结构，展示文本由结构生成。

5. **质量、组合、重复抑制、风暴、静默、质量降级等控件无完整持久化**
   - 页面有控件不代表规则实体有字段。
   - 解决：所有字段必须进入 `ruleForm`、规则 schema、reducer 校验和版本快照。

6. **通知快照字段不匹配**
   - 页面使用 `policyCode`、`policyOverride` 和临时 `policyDraft`。
   - 当前发布快照使用 `rule.policy`，可能保存为 `--`，临时调整的渠道、接收人、频率、升级和重试配置会丢失。
   - 解决：保存完整 `notificationConfig`，发布时深拷贝到版本快照。

7. **规则校验过弱**
   - 当前 reducer/actions 主要校验 code/name。
   - 必须增加设备、绑定、指标、类型、单位、量程、阈值、恢复、通知和治理参数校验。

8. **回测和存模板目前只是演示入口**
   - 当前回测主要展示 seed 统计，不一定使用当前未保存输入。
   - “存为模板”目前不能只 toast 成功而不产生实体。
   - 若当前版本不实现真实回放/模板持久化，应明确标注“演示参考”或暂时禁用入口，不得给出虚假成功提示。

## 2. 产品目标和术语

### 2.1 核心术语

| 术语 | 定义 |
|---|---|
| 规则 | 一个设备/数据源/指标目标上的一套可执行报警配置；每条规则独立拥有 code 和版本 |
| 目标 | 规则实际作用的设备、绑定、数据源、指标组合 |
| 模板 | 排除设备绑定后的可复用配置，包含触发、恢复、通知和治理参数 |
| 批次 | 一次批量生成或发布的任务，拥有 batchId、模板引用和逐目标结果 |
| 配置组 | 批量目标按指标语义、单位、数据类型、量程、设备型号等特征分出的同质组 |
| 草稿 | 可编辑、不会触发报警的规则版本 |
| 已发布 | 当前生效、允许触发新报警的规则版本 |
| 活动报警 | 尚未关闭的报警事件；同一规则目标的重复触发可合并计数 |
| 恢复 | 指标满足恢复条件并达到稳定要求，报警进入“已恢复待关闭”或按规则关闭 |
| 关闭 | 报警事件生命周期终点，不等同于指标刚刚恢复 |

### 2.2 批量创建的正确定位

批量创建不是“把多个指标塞进一条规则”，而是：

```text
一次选择多台设备上的相同/同类指标
→ 按指标特征和设备特征自动分组
→ 每组套用同一模板
→ 生成 N 条彼此独立的规则草稿
→ 逐条预览、校验和调整
```

示例：

```text
1号空压机 / 排气温度
2号空压机 / 排气温度
3号空压机 / 排气温度
```

最终生成：

```text
R-B001-001：1号空压机排气温度高温报警
R-B001-002：2号空压机排气温度高温报警
R-B001-003：3号空压机排气温度高温报警
```

多指标 AND/OR、联锁、工艺组合属于“组合规则”，不进入普通同类指标批量入口。

## 3. 单条规则目标功能设计

### 3.1 弹窗总体结构

将长弹窗组织为以下四个明确区域，可使用 Card、Steps 或分组标题，但不要把所有输入平铺成无法理解的长表单。

```text
① 基础信息与适用对象
② 触发条件
③ 恢复条件
④ 告警治理与通知
```

底部操作：

```text
取消 | 保存草稿 | 预览配置 | 保存并发布
```

编辑已发布规则时，顶部显示提示：

```text
本次修改将生成新草稿/新版本，不覆盖历史报警快照。
```

### 3.2 基础信息与适用对象

#### 必填字段

| 字段 | 类型 | 规则 |
|---|---|---|
| 规则名称 | Input | 必填，2~100 字，不允许纯空格 |
| 规则类型 | Select | 阈值 / 状态 / 质量 / 组合；编辑已发布规则时类型不可直接切换，需复制为新规则 |
| 报警等级 | Select | 紧急 / 重要 / 一般 / 提示 |
| 设备 | Cascader/Select | 仅可选择存在且可见的 canonical deviceId |
| 子设备/来源 | Cascader | 必须来自当前启用绑定 |
| 指标 | Cascader/Select | 必须属于当前绑定且处于启用状态 |

#### 建议字段

| 字段 | 类型 | 规则 |
|---|---|---|
| 规则说明 | TextArea | 说明报警含义和适用工况 |
| 可能原因 | TextArea | 展示于报警详情 |
| 处置建议 | TextArea | 展示于报警详情/通知 |
| 适用设备型号 | 展示 | 从绑定和设备资料推导，不允许手工伪造 |
| 单位/量程/精度 | 只读 | 从指标元数据展示 |
| 当前数据质量 | 只读 | GOOD/BAD/无数据/延迟等 |
| 当前已有规则 | 只读提示 | 显示同目标同类型规则及状态 |

规则名称建议自动生成但允许修改，例如：

```text
{设备名称}-{指标显示名}-{触发类型}报警
```

### 3.3 目标数据模型

规则不能只保存设备名称和 metricCode，必须固化目标引用：

```js
{
  target: {
    deviceId: 'DEV-001',
    deviceCode: 'MT2024A1201',
    bindingId: 'BIND-DEV001-01',
    bindingVersion: 3,
    sourceId: 'IOT-D-10001',
    sourceCode: 'IOT-D-10001',
    metricCode: 'M.spindle_temp',
    metricVersion: 1,
    metricName: '主轴温度',
    unit: '℃',
    dataType: 'number',
    range: { min: 0, max: 150 },
  },
}
```

`deviceCode` 仅用于展示，`deviceId` 是业务主键。规则运行和事件归属必须使用 canonical `deviceId + sourceId + metricCode`。

## 4. 触发条件设计

### 4.1 阈值规则

支持：

- 越上限：`value > threshold`
- 越下限：`value < threshold`
- 区间外：`value < low OR value > high`
- 区间内：`low <= value <= high`（仅在明确业务需要时使用）

结构：

```js
triggerConfig: {
  type: 'threshold',
  mode: 'upper', // upper | lower | rangeOut | rangeIn
  operator: '>',
  threshold: 80,
  low: null,
  high: null,
  unit: '℃',
  durationSec: 60,
  validSamples: null,
}
```

区间结构：

```js
triggerConfig: {
  type: 'threshold',
  mode: 'rangeOut',
  low: 0.6,
  high: 0.8,
  unit: 'MPa',
  durationSec: 30,
}
```

校验：

- `low < high`；
- 阈值必须在指标量程内，除非用户明确勾选“允许超量程工程阈值”并填写原因；
- `durationSec >= 0`；普通模拟量建议最小 1 秒，状态类才允许 0；
- 数值型指标才允许阈值模式；
- 单位必须与指标单位一致或存在明确换算关系；
- 同目标同规则类型不得存在重复的已发布规则。

### 4.2 状态规则

状态规则不得保存成“阈值 80”。结构：

```js
triggerConfig: {
  type: 'state',
  abnormalValues: ['FAULT', 'ESTOP'],
  normalValues: ['RUN', 'STANDBY'],
  durationSec: 0,
  unit: null,
}
```

要求：

- 指标必须是枚举/状态类；
- 异常状态至少一个；
- 正常状态至少一个；
- 异常状态和正常状态不能重叠；
- 状态恢复持续时间可配置，默认 30 秒；
- 不显示无意义的阈值、回差输入。

### 4.3 质量规则

质量规则监控数据链路，不要求普通指标阈值：

```js
triggerConfig: {
  type: 'quality',
  mode: 'outage', // outage | invalidRate | invalidCount | delay
  durationMin: 5,
  invalidRatePercent: null,
  invalidCount: null,
  delaySec: null,
  qualityCode: 'GOOD',
}
```

不同模式必填项：

- `outage`：中断持续分钟；
- `invalidRate`：BAD 占比阈值 + 持续分钟；
- `invalidCount`：连续无效条数 + 采样上下文；
- `delay`：最大允许延迟秒数 + 持续时间。

质量规则必须明确是否绑定设备、绑定来源，不能默认读取全局聚合数据而无范围说明。

### 4.4 组合规则

组合规则单独进入高级模式，保存条件树，不允许只保存展示文案：

```js
triggerConfig: {
  type: 'combo',
  operator: 'AND',
  windowSec: 300,
  conditions: [
    {
      target: { deviceId: 'DEV-001', sourceId: 'IOT-D-10001', metricCode: 'M.spindle_temp' },
      operator: '>',
      value: 80,
      unit: '℃',
      durationSec: 60,
    },
    {
      target: { deviceId: 'DEV-001', sourceId: 'IOT-D-10001', metricCode: 'M.coolant_temp' },
      operator: '<',
      value: 10,
      unit: '℃',
      durationSec: 60,
    },
  ],
}
```

组合规则要求：

- 条件至少 2 个；
- 每个条件目标独立有效；
- AND/OR 必须明确；
- 时间窗口必须大于 0；
- 组合规则不进入普通“同类指标批量新建”入口；
- 删除/新增条件必须真实更新数组，不能只弹 message。

## 5. 恢复条件设计

### 5.1 恢复方式

提供三种恢复口径：

1. **自动恢复并关闭**：普通温度、压力、液位等指标恢复后自动关闭；无业务关联时可直接关闭。
2. **恢复后业务闭环**：指标恢复后进入“已恢复待关闭”，要求维修验收、停机结束或业务动作完成后关闭。
3. **恢复后人工确认关闭**：恢复后必须由人员填写恢复证据和关闭原因。

恢复方式不能只保存展示字符串，应保存：

```js
recoveryConfig: {
  mode: 'auto', // auto | business | manual
  closeMode: 'auto', // auto | afterBusiness | manual
}
```

### 5.2 上限/下限恢复

上限触发示例：

```text
触发：温度 > 80℃
恢复：温度 <= 75℃，持续 30 秒
```

下限触发示例：

```text
触发：压力 < 0.60MPa
恢复：压力 >= 0.65MPa，持续 30 秒
```

支持两种阈值设置方式：

- 按回差计算：恢复值 = 触发值 ± deadband；
- 直接指定恢复阈值：用户输入实际恢复值。

结构：

```js
recoveryConfig: {
  mode: 'auto',
  condition: {
    type: 'hysteresis',
    direction: 'upper',
    thresholdMode: 'deadband', // deadband | explicit
    triggerValue: 80,
    recoveryValue: 75,
    deadband: 5,
    unit: '℃',
  },
  stabilize: {
    durationSec: 30,
    minValidSamples: null,
    qualityRequired: 'GOOD',
    invalidDataPolicy: 'hold', // hold | resetTimer | ignoreSample
    rebreachPolicy: 'resetTimer',
  },
  notifyOnRecover: true,
}
```

### 5.3 区间恢复

触发：

```text
压力 < 0.60MPa 或压力 > 0.80MPa
```

恢复：

```text
0.65MPa <= 压力 <= 0.75MPa，持续 30 秒
```

上下回差必须独立：

```js
condition: {
  type: 'range',
  triggerLow: 0.6,
  triggerHigh: 0.8,
  recoveryLow: 0.65,
  recoveryHigh: 0.75,
  lowDeadband: 0.05,
  highDeadband: 0.05,
  unit: 'MPa',
}
```

校验：

```text
triggerLow < triggerHigh
recoveryLow < recoveryHigh
triggerLow <= recoveryLow <= recoveryHigh <= triggerHigh
```

不得使用同一个 `deadband` 状态同时绑定上下两个 InputNumber。

### 5.4 状态、质量、组合规则恢复

#### 状态规则

```js
recoveryConfig: {
  mode: 'auto',
  condition: {
    type: 'state',
    normalValues: ['RUN', 'STANDBY'],
  },
  stabilize: { durationSec: 30, qualityRequired: 'GOOD' },
}
```

#### 质量规则

```js
recoveryConfig: {
  mode: 'auto',
  condition: {
    type: 'quality',
    requiredQualityCode: 'GOOD',
    subscriptionHealthy: true,
    maxDelaySec: 10,
  },
  stabilize: { durationSec: 120, invalidDataPolicy: 'resetTimer' },
}
```

#### 组合规则

- AND：全部子条件回到恢复带并稳定后恢复；
- OR：所有处于触发态的子条件均恢复后恢复；
- 每个子条件有自己的恢复配置；
- 组合条件恢复不能只保存一段描述文字。

### 5.5 恢复与关闭必须分离

状态流程：

```text
已触发 → 已确认 → 处理中 → 已恢复待关闭 → 已关闭
```

- 指标满足恢复条件：进入“已恢复待关闭”；
- 自动恢复且无业务关联：可由系统自动关闭；
- 有维修工单/停机事实：必须等待业务闭环；
- 人工关闭：必须填写恢复证据和关闭原因；
- 关闭后再次超限：新建报警事件，并关联上一事件，不继续吞并历史事件。

## 6. 告警治理与通知配置

### 6.1 重复报警抑制

将以下概念拆开配置：

```js
suppressionConfig: {
  mergeActiveEvent: true,
  countRepeatedTrigger: true,
  remindEnabled: true,
  remindIntervalMin: 5,
  maxRemindCount: null,
  createNewAfterClose: true,
}
```

说明：

- 活动事件未关闭期间，命中同一 dedupeKey 时合并计数；
- 重复提醒不新建事件；
- 报警关闭后再次触发必须新建事件；
- `remindIntervalMin >= 1`；
- 抑制配置必须写入规则版本快照。

### 6.2 报警风暴保护

```js
stormConfig: {
  enabled: true,
  windowMin: 60,
  maxEvents: 3,
  scope: 'sameRule', // sameRule | sameDevice | deviceGroup | sameMetric
  overflowAction: 'merge', // merge | downgrade | pauseNew
  notifyOnStart: true,
  notifyOnEnd: true,
}
```

校验：

- `windowMin > 0`；
- `maxEvents >= 1`；
- 风暴保护不能替代正常重复抑制；
- 显示“统计窗口、上限、合并范围、超限动作”，不要只显示“≤3条/小时”。

### 6.3 静默策略统一口径

不能同时让用户在规则级和通知策略级分别配置互相冲突的静默时段。

建议：

```js
silenceConfig: {
  source: 'template', // template | override | none
  enabled: true,
  windows: [{ start: '22:00', end: '07:00', timezone: 'Asia/Shanghai' }],
  overrideReason: null,
}
```

界面必须显示：

```text
模板默认：22:00-07:00
本规则覆盖：23:00-06:00
最终生效：23:00-06:00
```

若 `policyDraft.silent` 与规则级覆盖同时存在，以规则级明确覆盖为准，并在保存模型中只保留一个最终生效结果。

### 6.4 通知策略模板和临时调整

选择通知策略后带出模板内容，但当前规则可以临时覆盖，不回写模板：

```js
notificationConfig: {
  templateCode: 'NP-IMPORTANT',
  templateVersion: 'V2',
  overridden: true,
  channels: ['站内', '短信'],
  receivers: ['李明', '张三'],
  firstNotifyMin: 0,
  repeatIntervalMin: 5,
  escalation: [
    { afterMin: 10, receivers: ['王强'], channels: ['电话'] },
  ],
  retries: 3,
  silence: { ...silenceConfig },
  notifyOnRecover: true,
}
```

保存和发布版本必须保存完整 `notificationConfig`，不能只保存 `policyCode`。发布快照不得读取不存在的 `rule.policy` 字段。

校验：

- 至少一个通知渠道；
- 站内通知为必选渠道时必须保留；
- 至少一个有效接收人；
- 重复间隔和重试次数不得为负；
- 升级节点时间必须递增；
- 关闭/恢复通知应明确是否沿用原接收人。

## 8. 规则状态机和动作设计

### 8.1 规则状态

推荐状态：

```text
草稿 → 校验中 → 校验通过 → 已发布 → 已停用
  ↑                              ↓
  └────────────── 已停用 ─────────┘
```

前端演示可以简化为：

```text
草稿 → 已发布 → 已停用
已停用 → 草稿
```

但必须满足：

- 草稿和已停用规则不得触发新报警；
- 已发布规则编辑时生成草稿/新版本，不直接改写当前发布版本；
- 发布成功才变为已发布；
- 发布失败保持弹窗和草稿内容。

### 8.2 Action API

在 `src/state/actions.js` 增加或调整以下接口：

```js
saveRuleDraft(ruleForm) => {
  ok: boolean,
  message: string,
  refs: { ruleCode, version }
}

saveAndPublishRule(ruleForm) => {
  ok: boolean,
  message: string,
  refs: { ruleCode, version }
}

publishRule(ruleCode) => {
  ok: boolean,
  message: string,
  refs: { ruleCode, version }
}

disableRule(ruleCode, reason) => ...

previewBatchRules(request) => {
  ok: boolean,
  message: string,
  refs: { batchId, result }
}

commitBatchDraft(request) => {
  ok: boolean,
  message: string,
  refs: { batchId, created, skipped, blocked, failed }
}

publishBatch(batchId, selectedRuleCodes) => ...
```

### 8.3 原子保存并发布

推荐新增 reducer action：`alarm/rule/saveAndPublish`。

单个 reducer action 内完成：

```text
读取当前 state
→ 构造规则
→ 完整校验
→ 写入草稿
→ 版本号递增
→ 写入不可变版本快照
→ 将规则状态改为已发布
→ 写入 history
→ 返回 refs
```

不得依赖 React setState 完成后再在同一事件函数中读取新 state。

### 8.4 幂等要求

- 单条保存可使用 `ruleCode + draftVersion` 防止重复提交；
- `saveAndPublish` 可使用 `rule-save-publish:{ruleCode}:{clientRequestId}`；
- 批量提交使用 `batchId` 或 `clientRequestId`，重复点击不能生成重复规则；
- 已存在同目标同类规则默认 skip，不覆盖。

## 9. 规则校验设计

建议新增 `src/domain/alarmRule.js`：

```js
export function validateRuleDraft(rule, context) {
  return {
    errors: [],
    warnings: [],
    normalizedRule: rule,
  };
}
```

### 9.1 阻断错误

以下情况必须阻止保存/发布：

- 规则名称为空或超长；
- 目标设备不存在；
- 目标绑定不存在、已停用或不属于该设备；
- 指标不存在、已停用或不属于该绑定；
- rule type 与指标数据类型不匹配；
- 阈值、区间、恢复阈值缺失；
- `low >= high`；
- 区间恢复带反转或为空；
- 阈值超量程且未填写允许原因；
- 持续时间、回差、限流、重复间隔出现负数或非法值；
- 状态规则异常/正常枚举为空或重叠；
- 组合规则条件少于 2 个；
- 通知策略缺少有效渠道或接收人；
- 已存在相同目标、相同规则类型、相同触发语义的已发布规则；
- 规则为联锁/高高高风险类型但没有必要审批标记（演示中可阻止普通入口）。

### 9.2 警告项

允许用户确认后继续：

- 阈值接近量程边界；
- 回差过小，存在震荡风险；
- 持续时间为 0；
- 接收人数量过多；
- 设备当前离线或数据长时间未更新；
- 预计批量目标数量异常增加；
- 同一设备同类指标近期报警频繁；
- 规则覆盖范围包含不同型号，系统已自动分组。

### 9.3 展示要求

校验结果必须区分：

```text
阻断错误：红色，不能提交
需确认警告：橙色，必须勾选确认
提示：蓝色，可继续
```

不能只弹一条模糊的“配置失败”。

## 10. 批量新建功能设计

### 10.1 入口

在 `/alarm-rules` 列表工具栏增加：

```text
新增规则
批量新建
```

保留原单条“新增规则”，避免用户误解多个指标共用一条规则。

### 10.2 第一步：选择范围和同类指标

批量弹窗/抽屉使用 Steps：

```text
1. 选择对象
2. 自动分组
3. 配置模板
4. 预览校验
5. 生成草稿
```

选择对象页面：

- 设备类型/设备组/车间/设备型号筛选；

- 展示匹配目标列表；
- 复选框选择多台设备的同一个或同类指标；
- 显示单位、量程、数据类型、已有规则、绑定状态和数据质量；
- 默认排除停用绑定；

列表列建议：

| 选择 | 设备 | 型号 | 子设备/来源 | 指标 | 单位 | 量程 | 已有规则 | 状态 |
|---|---|---|---|---|---|---|---|---|

### 10.3 自动分组算法

目标必须满足以下条件才能进入同一配置组：

```text
指标语义/metricTemplateKey 相同
+ 数据类型相同
+ 单位兼容
+ 触发模式兼容
+ 设备型号/量程满足同组规则
```

推荐分组键：

```js
groupKey = [
  metricTemplateKey,
  dataType,
  normalizedUnit,
  `${range.min}:${range.max}`,
  deviceModel,
].join('|');
```

分组结果示例：

```text
已选择 8 个目标，自动识别为 2 个配置组：
A 型空压机 / 排气温度 / ℃ / 0~150℃：5 台
B 型空压机 / 排气温度 / ℃ / 0~200℃：3 台
```

差异过大的目标必须：

- 自动拆成不同组；或
- 标记为不可批量并说明原因；
- 不得静默使用第一条目标的阈值复制到全部设备。

### 10.4 模板配置

可统一配置：

- 报警等级；
- 触发模式；
- 持续时间；
- 恢复方式；
- 恢复稳定时间；
- 通知策略；
- 重复抑制；
- 风暴保护；
- 静默策略。

必须允许按组覆盖：

- 触发阈值；
- 恢复阈值/回差；
- 量程比例；
- 额定值比例；
- 设备型号特有的接收人或处置建议。

阈值方式支持：

```text
统一绝对值
按量程比例
按设备型号分组
指定目标额定值比例
```

### 10.5 批量预览

| 目标 | 规则名称 | 触发条件 | 恢复条件 | 通知 | 结果 | 说明 |

| DEV-001/排气温度 | ... | >90℃/60s | <=85℃/30s | NP-IMPORTANT | 可创建 | - |
| DEV-002/排气温度 | ... | >90℃/60s | <=85℃/30s | NP-IMPORTANT | 跳过 | 已有已发布规则 |
| DEV-003/排气温度 | ... | >110℃/60s | <=105℃/30s | NP-IMPORTANT | 可创建 | B型设备组 |

## 12. 报警事件和恢复联动

### 12.1 触发时

`alarm/raise` 必须：

1. 只读取 `status === '已发布'` 且在有效期内的规则；
2. 验证目标绑定和指标仍有效；
3. 记录 `ruleCode`、`ruleVersion`、`bindingVersion`、`sourceId`、`metricCode`；
4. 记录触发值、阈值、单位、sourceTime、receiveTime、qualityCode；
5. 保存 `ruleSnapshot` 或版本快照引用；
6. 只对活动事件使用 dedupeKey 合并。

### 12.2 恢复时

恢复证据至少包括：

```js
{
  recoveredAt: at,
  recoveredValue: sample.value,
  recoveredUnit: sample.unit,
  sourceTime: sample.sourceTime,
  qualityCode: sample.qualityCode,
  ruleVersion: rule.version,
  recoverySnapshot: rule.recoveryConfig,
}
```

### 12.3 关闭时

统一使用 `closeBlockers`：

- 业务闭环规则：维修工单未验收不得关闭；
- 关联停机未结束不得关闭；
- 人工关闭必须填写关闭原因；
- 自动恢复类无业务关联可自动关闭；
- 关闭后再次触发创建新事件。

## 14. 测试和验收方案

### 14.1 单条规则 reducer 场景

至少增加 Node 可执行的 reducer 级验证：

1. 新建完整阈值规则，保存草稿后状态为草稿；
2. 草稿不能触发报警；
3. 原子保存并发布后状态为已发布；
4. 发布版本为 V1，并有完整 trigger/recovery/notification 快照；
5. 修改已发布规则生成草稿，不改变已发布版本快照；
6. 发布后版本递增为 V2；
7. 停用后不能触发新报警；
8. 缺设备、缺指标、停用绑定、单位不一致、阈值反转均被阻断；
9. 通知临时调整进入规则和版本快照；
10. 恢复配置进入恢复证据和历史事件快照。

### 14.2 恢复条件验收

1. 上限：80℃触发，75℃以下持续 30 秒恢复；
2. 下限：0.60MPa触发，0.65MPa以上持续 30 秒恢复；
3. 区间外：0.60~0.80MPa外触发，0.65~0.75MPa持续恢复；
4. 区间上下回差可独立修改；
5. 无效数据按 hold/resetTimer 处理，不得错误自动恢复；
6. 恢复过程中再次超限，计时归零；
7. 有维修工单时指标恢复只能进入已恢复待关闭；
8. 人工关闭缺少证据/原因时被阻断；
9. 关闭后再次超限生成新事件。

### 14.3 批量创建验收

1. 选择 3 台相同型号设备的同一指标，生成 3 条独立草稿；
2. 规则 code、target、metricCode、绑定版本各自独立；
3. 同批次拥有相同 batchId/templateId；
4. 选择不同型号设备时自动拆分为不同配置组；
5. 温度和压力混选时阻止或拆分，并显示原因；
6. 已有规则默认跳过，不覆盖；
7. 停用绑定目标进入阻断项；
8. 一条目标失败不污染其它成功目标，结果页显示 created/skipped/blocked/failed；
9. 重复提交同一 batchId 不重复生成规则；
10. 批量只生成草稿，未发布前不能触发报警；
11. 批量发布后每条规则拥有独立版本快照；
12. 页面刷新后批次和规则仍来自 DemoStore 持久化状态。

### 14.4 UI 和全路由验证

- 全部路由空白数为 0；

## 18. 完成判定

本方案全部完成的判定标准不是“弹窗字段变多”，而是以下闭环全部成立：

```text
表单输入
  ↓
结构化规则模型
  ↓
领域校验
  ↓
DemoStore 原子保存
  ↓
草稿/发布状态机
  ↓
规则版本快照
  ↓
报警触发使用已发布版本
  ↓
恢复使用恢复配置
  ↓
历史报警保存触发/恢复证据
  ↓
同类指标批量生成多条独立规则
  ↓
批次可预览、可追踪、可重试
```

只要其中任一环节仍然是页面 toast、硬编码文本、旧 seed 数字或未落库控件，就只能标记为“演示占位”，不能宣称该功能已经完成。
